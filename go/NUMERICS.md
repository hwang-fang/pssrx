# 演算規約

丸めや剰余の扱いを Go の標準的な演算からずらしている箇所がある。その一覧と、
なぜずらす必要があるのか、そしてずらさなかった場合に何がどれだけ変わるかの
実測値。

なぜ効くのか。intg の方位角は `[0, 2pi)` を 32 bit に量子化して書き出すので、
1 LSB は約 1.5e-9 rad しかない。ドウェル間の内挿ではビーム中心通過時刻が
方位の基準になり、その時刻は ns 単位に丸められる。つまり浮動小数点の
最下位ビットの差が、そのままファイルの中身の差として表に出る。

## 実測: Go の素の演算に戻すと何が変わるか

KX90 の 2026-06-10 全日（1440 ファイル / 29,288,396 レコード）で、
規約を 1 つずつ Go の素の演算へ差し替えて出力を比較した結果。

| 差し替え | 相違ファイル | 相違レコード | 判断 |
| --- | --- | --- | --- |
| 偶数丸め → `math.Round` | 298 / 1440 | 699 | **規約を維持** |
| 床除算・床剰余 → `/` と `%` | 0 | 0 | 素の演算へ戻した |
| pairwise 総和 → 逐次加算 | 0 | 0 | 素の演算へ戻した |
| `[0,2pi)` 畳み込み → `math.Mod` | 0 | 0 | **規約を維持**（下記） |

差が 0 だった 2 つは素の Go の演算に戻してある。読む側にとって、
標準と違う演算がそこにある理由を毎回確かめずに済むほうが安全なため。

### 偶数丸めを維持する理由

ブラケット内挿の質問時刻 `t0 + round(a + P(s) + eps*s)` で、丸めの対象が
0.5 ちょうどに当たる質問が実データに一定数ある。この値の大きさ（約 4e9）
では float64 の刻みが 4.8e-7 なので、0.5 に当たる確率はレコードあたり
おおよそ 5e-7、1 日 2900 万レコードで数百発という計算になり、実測の
699 レコードと符合する。

丸めが 1 ns 変わると、方位の内挿の重み `w = (t - center) / span` が
`1/4.04e9` だけ動き、方位角にして約 1.06 LSB ずれる。

`testdata/golden/rounding` がこの退行を検出する。

### `[0,2pi)` の畳み込みを維持する理由

こちらは実データの配置では差が 0 だったが、**維持が必要**と判断した。

方位の内挿の重みはドウェル先頭で負になるため、`stAzimuth + 2pi*rot*w` は
局方位が小さい配置（SSR のほぼ真北に測定局がある場合）で負になる。
`math.Mod` は被除数の符号を引き継ぐので負のまま返し、その値を uint32 へ
変換すると Go の仕様上「実装依存」の結果になる。amd64 では 2^32 で
巻き戻り、arm64 では 0 に飽和する。

検証に使った局方位 0.225 度の配置では、amd64 上でも全 60 ファイル・
6,950 レコードが 2 LSB ずれた。arm64 なら方位角が 0 になる。

`analyze.wrapAngle` に閉じ込め、`TestWrapAngle` が範囲の不変条件を検証する。

## 規約どおりでよい箇所

- **整数列の平均**。合計を整数のまま取り、最後に 1 度だけ割る。呼び出し側が
  渡すのは残差（ns 単位、高々 1e5 程度）と段数だけなので、合計が int64 を
  溢れることも float64 の厳密表現域 2^53 を出ることもない。
- **出力レコードの整列**。ブラケットは半開区間で連結されるので、出力の
  タイムスタンプに重複が構造的に発生しない。安定ソートかどうかは効かない。
- **探索窓の 256 ns 量子化**。連鎖検出の窓の端は、int64 のタイムスタンプ
  ではなく float64 に変換した値の上で決まる。Unix ナノ秒（約 1.78e18）
  では float64 の刻みが 256 ns あるため、窓の端はこの粒度に丸まる。
  窓幅は 20 us なので実害は無い。

## 厳密には守れなかった箇所

放物線フィットの正規方程式 `X^T X` の組み立てと、3x3 の LU 分解。
どちらも加算順序で最下位ビットが動くが、比較対象の実装が CPU の派生機能で
カーネルを切り替えるため、順序を完全には再現できない。

順序の候補を実測した結果:

| 正規方程式の組み立て | 一致 |
| --- | --- |
| 素朴な逐次加算 | 113/144 |
| FMA | 126/144 |
| pairwise | 97/144 |
| 4 アキュムレータ | 90/144 |

LU 分解は 16 通り（逆数乗算か除算か・列方向か行方向か・FMA の有無・
ピボット同値時の先勝ちか後勝ちか）を総当たりし、最良の組み合わせで
30/36 がビット一致、残りも 1〜2 ulp。採用した順序は `Solve3` の
コメントに書いてある。

**追いかけない判断をした。** 仮に一致させても別の CPU で壊れるうえ、
差が出力に届かないことを実測で確認できたため。

| 量 | 最大の差 | 判定に効く閾値 |
| --- | --- | --- |
| 頂点時刻 | 2.1e-7 ns | 1 ns 丸め（境界は 0.5 ns） |
| ピーク振幅 | 3.2e-14 dB | 3.0 dB |
| 残差 RMS | 相対 7.7e-15 | 1.0 |

頂点時刻が 1 ns 変わる確率はドウェルあたり約 4e-7 で、仮に変わっても
方位角への影響は 1 LSB に留まる。`TestNormalEquations3Tolerance` が
0.5 ns の 500 倍の余裕（1e-3 ns）を上限として固定し、`TestSolve3` が
LU の ulp 上限を 2 に固定している。

実データ 3170 万レコードで出力が完全一致していることから、この見積もりは
実用上正しい。

## 入力の整列が結果に与える影響

qpkx には時刻の逆行を含むファイルが相当数ある（README 参照）。
読み込み時に整列するかどうかで**解析結果そのものが変わる**。
KX90 の 1 時間（2026-06-10 00:00–01:00）で両方の設定を比べた結果:

| 項目 | 値 |
| --- | --- |
| 出力ファイル | 60 中 **19 が相違** |
| 出力レコード数 | 1,219,906（両者同数） |
| 片方にしか無いレコード | 各 4,023 |
| 同一時刻で方位角が相違 | **53,490（全体の 4.4%）** |
| 方位角の差 | 最大で数万 LSB（1 LSB = 1.46e-9 rad） |

これは丸め誤差の水準ではなく、ドウェルの検出結果とブラケットの張り方が
実際に変わっていることを意味する。整列しない場合、二分探索は非単調な
配列に対して未定義の位置を返すので、そもそも結果を信頼できない。

どちらが「正しい」かはデータの生成側——受信機が時刻の逆行するファイルを
書く理由——を確かめないと決められない。現状は整列を既定としている。
