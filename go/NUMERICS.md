# 数値の一致について

Python / numpy 実装と `.intg` をバイト単位で一致させるために、Go 側で
明示的に合わせている規則と、合わせきれずに許容差として固定した箇所の記録。

すべて `tools/gen_npvectors.py` が**実際の numpy 2.5.1 / Python 3.14.6 から
生成したテストベクタ**に対して検証している。numpy の実装を読んで推測した
ものではない。

## 完全に一致させた規則

| 規則 | Python / numpy | Go の素朴な書き方 | 実装 |
| --- | --- | --- | --- |
| 丸め | `round()` / `np.rint` は**偶数丸め** | `math.Round` は 0 から離れる方向 | `npcompat.RoundHalfEven` |
| 整数除算 | `//` は**床除算** | `/` は 0 方向切り捨て | `npcompat.FloorDiv` |
| 剰余 | `%` は除数の符号 | `%` は被除数の符号 | `npcompat.FloorMod` |
| 実数剰余 | `np.mod` は除数の符号 | `math.Mod` は被除数の符号 | `npcompat.Mod` |
| 総和 | `np.sum` は pairwise summation | 逐次加算 | `npcompat.Sum` |
| 型変換 | float64 → 整数は**切り捨て** | 同じだが四捨五入と混同しやすい | `npcompat.TruncToUint32` |
| 中央値 | `np.median` | — | `npcompat.Median` |
| 二分探索 | `np.searchsorted` | — | `npcompat.SearchSorted{Left,Right}` |

いずれもテストベクタに対してビット単位で一致する。

### 特に壊れやすかった箇所

- `analyze.py` の `phase_shift % L`。`phase_shift = ch_b.phase0 - ch_a.phase0`
  は**負になりうる**ため、Go の `%` をそのまま使うと符号が反転して
  連結先の候補がまるごと変わる。
- `np.mod(azimuth, 2*pi)`。方位の内挿の重み `w` はドウェル先頭で負になるので
  ここも同様。
- `int(around_time_sec * 1e9)`。`4.1` 秒は `4099999999` ns になる。
  四捨五入してはならない。
- `np.searchsorted(t, ti + exp - gate)` の **256 ns 量子化**。
  `t` は int64 だが比較スカラが float64 なので numpy は共通型 float64 へ
  昇格させる。Unix ナノ秒（約 1.78e18）では float64 の ulp が 256 ns あるため、
  探索窓の端が 256 ns 刻みに丸まる。Go 側も `float64` へ変換してから
  二分探索することでこの精度落ちを再現している。

### 一致するが自明でなかった箇所

- `np.mean` を int64 配列に適用した場合。numpy は float64 アキュムレータで
  合計するが、要素も部分和も 2^53 未満の整数に収まる範囲では合計は厳密なので、
  int64 で合計してから 1 回割る実装とビット一致する。呼び出し側が渡すのは
  残差（ns 単位、高々 1e5 程度）と段数だけなのでこの前提は常に成り立つ。
- `math.Sqrt` と `math.Atan2`。Go と glibc で 1 ulp 違う可能性を懸念したが、
  実データの座標に対しては 16 進表現まで一致した（`TestStationGeometryMatchesPython`）。
- `np.sort(order="timestamp")` が不安定ソート（quicksort）である点。
  出力レコードにタイムスタンプの重複が構造的に発生しない（ブラケットが
  半開区間で連結されるため）ので、`slices.SortStableFunc` と一致する。
  ゴールデンの全 300 ファイルで重複ゼロを確認済み。

## 許容差として固定した箇所

### 正規方程式の行列積（BLAS dgemm）

放物線フィットの `x.T @ x` と `x.T @ y` は numpy が BLAS の dgemm を呼ぶ。
総和順序が CPU 派生のカーネル選択に依存するため、Go 側で再現できない。

素朴・FMA・pairwise・4 アキュムレータの 4 通りを実測した一致率:

| 実装 | 一致 |
| --- | --- |
| 素朴な逐次加算 | 113/144 |
| FMA | 126/144 |
| pairwise | 97/144 |
| 4 アキュムレータ | 90/144 |

どれも完全一致しない。仮に一致させても OpenBLAS のカーネルは CPU の
派生機能で切り替わるため別マシンで壊れる。よって**追いかけない**。

代わりに、その差が最終出力に効かないことを物理量で担保している。
頂点時刻 `center` の差は最大 **2.1e-7 ns**（丸め境界は 0.5 ns）、
`peak` は 3.2e-14 dB（閾値 3.0 dB）、`rms` は相対 7.7e-15（閾値 1.0）。
`center` が 1 ns 変わる確率はドウェルあたり約 4e-7 で、仮に変わっても
方位角への影響は 1 LSB に留まる。`TestNormalEquations3Tolerance` が
0.5 ns の 500 倍の余裕（1e-3 ns）を上限として固定している。

### LU 分解（LAPACK dgesv）

`np.linalg.solve` は LAPACK の `dgesv` を呼ぶ。実装バリアント 16 通り
（逆数乗算か除算か・列方向か行方向か・FMA の有無・ピボット同値時の
先勝ちか後勝ちか）を総当たりで実測し、最良の組み合わせを採用した。

- `dgetf2`: 部分ピボットは列内の |値| 最大、同値なら先に現れた行
- `dgetf2`: 除算ではなく逆数を 1 回作って掛ける（`x/p` ではなく `x*(1/p)`）
- `dtrsv`: 前進・後退代入は列方向。後退代入では `A02*x2` を `A01*x1` より先に引く

これで 30/36 がビット一致、残りも 1〜2 ulp。numpy が呼ぶのは参照 LAPACK
ではなく OpenBLAS の `dgetrf` なので、これ以上は同様に CPU 依存になる。
`TestSolve3MatchesLAPACK` が 2 ulp を上限として固定している。

**上記 2 点の許容差にもかかわらず、実データ 3170 万レコードでバイト一致を
達成している**（README の検証状況）。理論上の差が実際には出力に現れないことは
実測で確認済み。

## ソートの影響

qpkx の時刻逆行（README 参照）に対して、読み込み時にソートするかどうかで
**解析結果そのものが変わる**。KX90 の 1 時間（2026-06-10 00:00–01:00）で
Python 実装を両方の設定で走らせた結果:

| 項目 | 値 |
| --- | --- |
| 出力ファイル | 60 中 **19 が相違** |
| 出力レコード数 | 1,219,906（両者同数） |
| 片方にしか無いレコード | 各 4,023 |
| 同一時刻で方位角が相違 | **53,490（全体の 4.4%）** |
| 方位角の差 | 最大で数万 LSB（1 LSB = 1.46e-9 rad） |

これは丸め誤差の水準ではなく、ドウェルの検出結果とブラケットの張り方が
実際に変わっていることを意味する。どちらが正しいかはデータの生成側
（受信機が時刻の逆行するファイルを書く理由）を確かめないと決められない。
